## 2024-05-27 - [CRITICAL] Prevent SSRF in webhook delivery via DNS resolution

**Vulnerability:** The application was vulnerable to Server-Side Request Forgery (SSRF) via webhook URLs. Webhooks were dispatched via `fetch` without validating the destination IP address, allowing an attacker to submit internal or loopback IPs (e.g., `127.0.0.1`, `169.254.169.254`) and force the server to interact with internal services or cloud metadata endpoints.
**Learning:** `fetch` inherently follows redirects, which can be leveraged to bypass initial URL string checks. Node's `dns/promises` combined with `net.BlockList` is an effective pattern for evaluating IPs prior to requesting them, but care must be taken to also block `redirect` behavior in `fetch` to prevent time-of-check to time-of-use (TOCTOU) bypasses via malicious redirect responses. IPv4-mapped IPv6 addresses must also be blocked in dual-stack environments.
**Prevention:** Always perform strict IP resolution and filtering (blocking loopbacks, private networks, cloud metadata ranges) before dispatching requests to user-controlled URLs. Configure `fetch` to `redirect: 'error'` or `'manual'` to prohibit redirect-based bypasses. Ensure API and unit tests use external mock domains like `example.com` instead of `127.0.0.1` when simulating failures.
